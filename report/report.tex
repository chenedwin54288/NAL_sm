\section{Motivation}

Internet Service Providers often use rate limiters to enforce a maximum traffic rate for a subscriber, an application 
class, or a traffic aggregate. A common implementation is a Token Bucket Filter (TBF): tokens are generated at a configured 
rate, packets consume tokens before transmission, and excess packets are either delayed in a queue (traffic shaping) or 
dropped when the queue is full (traffic policing). This creates a mismatch with 
loss-based TCP congestion control. TCP Reno and similar congestion-control algorithms grow 
\code{cwnd} until loss and then reduce it. Behind a per-flow limiter, this probing can prevent the connection from using 
the full allowed rate smoothly: the sender repeatedly overshoots the limiter, fills the queue, loses packets, and enters 
recovery. The central question is therefore: \textbf{if the limiter parameters are known, or can be inferred, can the endpoint 
choose a better sending window and use the available rate with less loss?}

Two previous semester projects studied this question in simulation. Friedli's work used ns-3 to test whether knowing the 
TBF parameters could improve TCP throughput by selecting a better window. The important result for this project is that 
the gain is largest when the queue is small; in that regime, the fixed-window algorithms improved throughput by about 
33\% for New Reno. Rimkevicius's work studied the complementary problem: how to infer the policing rate from packet 
arrivals, especially from the receiver side.

However, both works were evaluated in a simulated environment, where the bottleneck, queue size, RTT, and packet losses are easy 
to control and observe. This project asks whether the same idea survives in a real physical setup. We built a two-machine 
Linux testbed connected through a lab router, added a TBF on the server-to-client path, instrumented the Linux TCP stack, 
and compared uncapped Reno-like behavior with capped windows. The resulting story is not simply that the formulas work 
or fail. Window capping does help strongly in the small-queue regime, matching the motivation from Friedli's result, but 
the physical setup exposes an additional effect: the server can enqueue bursts into the TBF faster than the TBF drains 
them. That enqueue pressure reduces the amount of queue space that can be treated as useful extra in-flight capacity.

\section{Background}

\subsection{Token-Bucket Policing and TCP Windows}

A TBF is described by three parameters: a token generation rate \(R_{\mathrm{tbf}}\), a burst size \(B\), and a queue limit \(Q_{\mathrm{config}}\). 
The token rate determines the long-term output rate. The burst size determines how many tokens can accumulate when the sender is idle or 
sending below the token rate. The queue limit determines how much traffic can wait for tokens before packets are dropped.

TCP controls sending through two windows. The congestion window (\code{cwnd}) is chosen by the congestion-control algorithm 
at the sender. The receive window (\code{rwnd}) is advertised by the receiver and expresses how much data the receiver is 
willing to accept. The effective sending window is approximately:

\[
W_{\mathrm{send}} = \min(\code{cwnd}, \code{rwnd}).
\]

Traditional loss-based algorithms such as TCP Reno and TCP Cubic grow \code{cwnd} until loss, then reduce it. This behavior is 
useful when loss indicates shared-network congestion, but it can be inefficient behind a per-flow TBF. If the user has a dedicated 
rate limit, the best behavior is often to send steadily at the token rate rather than probing above it and recovering from 
avoidable drops.

\subsection{Prior Work in ns-3}

Friedli's project, \emph{Revisiting Traffic Congestion Control Protocols at the Last Mile}, studied how TCP New Reno, Cubic, 
and BBR interact with a TBF in ns-3. The key observation was that the maximum useful amount of in-flight data is related 
to the BDP and to the bottleneck queue. The project proposed:

\[
W_1 = \bdp + Q_{\mathrm{config}} - \mss
\]

and later found that a simpler cap,

\[
W_2 = \bdp + \mss,
\]

also reaches the TBF rate in many configurations while avoiding buffer build-up. In simulation, \textbf{the algorithms improved 
small-buffer cases by roughly 33\% for New Reno and 17\% for Cubic}. For larger queues or larger bursts, default TCP already 
performs closer to the TBF rate, so the relative gain decreases.

Rimkevicius's project, \emph{Inference of Traffic Differentiation Policing Rate}, studied how to infer \(R_{\mathrm{tbf}}\) 
from one traffic trace. It compared sender-side and receiver-side methods. The most accurate method was \textbf{receiver-side 
cumulative-arrival differentiation}: compute cumulative received bytes over time, differentiate the curve, and use a 
statistic such as the median or a lower percentile of the derivative samples. Loss-based methods were more 
conservative, but often underestimated the true policing rate. This project used that work as the natural 
path toward a receiver-driven system: first infer \(R_{\mathrm{tbf}}\), then choose a window cap from the inferred rate.

\subsection{What Changes in a Physical Linux Setup}

The ns-3 model hides several details that matter in Linux. In Linux, packets normally pass through a queueing discipline, 
or qdisc, before they are handed to the network driver. A TBF is one such qdisc: it releases packets only when enough 
tokens are available, and otherwise keeps them in a bounded waiting queue. If that queue reaches the configured 
\code{limit}, new packets cannot simply wait forever and are dropped~\cite{tc,tctbf}. It is straightforward to attach TBF to the server's 
egress path, so the server-to-client traffic is shaped before leaving the server. Applying the same mechanism after 
traffic has already arrived at the client would require a more complex ingress setup, such as redirecting packets through 
an \code{ifb} virtual interface. For reproducibility, the stable experiments therefore placed the TBF on server egress, 
which emulates a forward-path bottleneck while keeping the limiter parameters directly under our control.

Second, the sender does not place one MTU-sized packet at a time into the qdisc. With TCP Segmentation Offload (TSO) 
and Generic Segmentation Offload (GSO), the kernel or NIC may handle large segments that are later split into 
MTU-sized packets. This produced large qdisc enqueue events and NIC requeues in early experiments, making 
the measured \code{cwnd} behavior difficult to interpret. The final automation disables TSO and GSO 
before applying the TBF.

Third, measuring \code{cwnd} at high frequency is itself difficult. Polling with \code{ss} cannot keep up 
with fast changes because it requires repeated Netlink dumps. Kernel logging with \code{pr\_info} 
gives better visibility, but Linux uses a finite ring buffer, so frequent logs are overwritten unless 
they are extracted and cleared during the transfer.

\subsection{Custom Congestion-Control Module}

The project then moved to a controlled bulk-transfer setup and implemented a custom Linux congestion-control module, 
\code{my\_cca}. This did not require editing and recompiling the whole Linux kernel. Instead, the project implemented 
a loadable TCP congestion-control module that registers itself with Linux's pluggable TCP congestion-control framework. 
This framework exposes a \code{struct tcp\_congestion\_ops}, where a module provides callbacks such as 
\code{ssthresh}, \code{cong\_avoid}, \code{undo\_cwnd}, and \code{pkts\_acked}~\cite{arianfar_tcp_cc}. 
Figure~\ref{fig:mycca_impl} shows the corresponding registration and logging code used by \code{my\_cca}. 
The module is Reno-style: it 
implements slow start, additive increase, Reno-like slow-start threshold reduction, and an undo callback. The important 
modification is a module parameter, \code{cwnd\_limit}. 
When this parameter is nonzero, both slow start and congestion avoidance apply:

\[
\code{cwnd} \leftarrow \min(\code{cwnd}, \code{cwnd\_limit}).
\]

When \code{cwnd\_limit = 0}, the cap is disabled and the module behaves as an uncapped Reno-like baseline. 
This made it possible to compare capped and uncapped behavior while keeping the same logging and analysis pipeline.

The module logs \code{cwnd}, RTT samples, bytes acknowledged, bytes sent, and a phase label whenever enough ACKs 
have passed or the phase changes. The phase label is derived from the Linux TCP congestion-control state first, and 
from the slow-start condition only if the socket is not already in a recovery state. In other words, the labels are 
assigned in the same priority order as the code:

\begin{itemize}
  \item \code{fast\_retransmit}: \code{icsk\_ca\_state} is \code{TCP\_CA\_Recovery}. This is the fast-recovery state entered after loss is inferred from duplicate ACKs or SACK information.
  \item \code{loss\_recovery}: \code{icsk\_ca\_state} is \code{TCP\_CA\_Loss} or \code{TCP\_CA\_CWR}. \code{TCP\_CA\_Loss} usually follows an RTO timeout, while \code{TCP\_CA\_CWR} means TCP is reducing \code{cwnd} after a congestion signal such as ECN or another congestion-window reduction event. This label therefore means ``loss or congestion-window reduction'', not necessarily a directly observed packet loss.
  \item \code{slow\_start}: the socket is not in \code{TCP\_CA\_Recovery}, \code{TCP\_CA\_Loss}, or \code{TCP\_CA\_CWR}, and \code{tcp\_in\_slow\_start(tp)} is true. In practice, this means \code{cwnd} is still below \code{ssthresh}.
  \item \code{congestion\_avoidance}: none of the previous conditions hold. This is the normal Reno additive-increase phase after slow start.
\end{itemize}

This ordering is important when reading the plots. A point is labeled as a recovery phase before the code checks 
whether it is below \code{ssthresh}; only non-recovery points can become \code{slow\_start}. Therefore, if a loss 
event reduces \code{cwnd} below the initial value or below \code{ssthresh}, the following samples may still be valid 
TCP behavior rather than an instrumentation error.

The module uses \code{pr\_info()} inside the ACK callback to log TCP state from the kernel. Logging every ACK was too 
expensive and quickly overwrote the kernel ring buffer. The final version logs every 100th ACK unless the TCP phase 
changes. A sequence number was added to detect missing log records.

\subsection{Handling Kernel Ring-Buffer Overwrite}


The first custom-module runs still produced misleading traces: for example, a 20 GiB transfer did not appear to start 
from the expected initial \code{cwnd}: 10. The cause was not TCP behavior, but instrumentation loss. By the time logs 
were extracted at the end of a transfer, early \code{pr\_info} records had already been overwritten in the \textbf{kernel ring buffer}.

In Linux kernel code, \code{printk()} and its convenience macros such as \code{pr\_info()} are the standard way to 
write diagnostic messages from inside the kernel. These messages go into the kernel log buffer, a finite ring buffer 
exported to user space through \code{/dev/kmsg}. The \code{dmesg} command reads this buffer, and \code{dmesg --clear} 
clears the records that have already been read~\cite{printk,dmesg}. 
In our module, each selected ACK event calls \code{pr\_info()} with the current \code{cwnd}, RTT sample, bytes 
acknowledged, bytes sent, TCP phase, destination IP, and destination port, as shown in Figure~\ref{fig:mycca_impl}. 
Because the log buffer has finite capacity, 
high-frequency \code{pr\_info()} calls can overwrite older records before the user-space analysis script reads them. 
This is why the early experiments appeared to miss the beginning of slow start.

\subsection{Final Automation Pipeline}

After the measurement path was reliable, the setup was wrapped into an automation pipeline. Figure~\ref{fig:final_auto_pipeline} 
shows the final system. The pipeline has two entry points. \code{client\_server/run.sh} performs one complete experiment 
on the server host, while \code{client\_server/run\_cwnd\_sweep.sh} repeatedly calls \code{run.sh}, starts the client over 
SSH, and aggregates the sweep outputs.

\begin{figure}[H]
  \centering
  \includegraphics[width=\textwidth]{final_auto_pipeline/sys_design.png}
  \caption{Final automation pipeline. \code{run.sh} prepares the Linux sender, starts the instrumented server, collects raw logs, and launches the per-run analysis. \code{run\_cwnd\_sweep.sh} wraps this process across many TBF and window configurations.}
  \label{fig:final_auto_pipeline}
\end{figure}

For a single run, \code{run.sh} turns user-specified parameters such as \code{--cca}, \code{--size-gib}, 
\code{--cwnd}, \code{--tbf-rate}, \code{--tbf-burst}, and \code{--tbf-limit} into a reproducible measurement:

\begin{enumerate}
  \item parse and validate the experiment options and required tools;
  \item create a temporary output directory under \code{DB/};
  \item reset the root qdisc on the selected server interface;
  \item install the TBF qdisc with the chosen token rate, burst size, and queue limit;
  \item disable TSO and GSO with \code{ethtool}, so packet and qdisc behavior are easier to interpret;
  \item if \code{my\_cca} is selected, rebuild, sign, unload, and reload the module with the requested \code{cwnd\_limit};
  \item start \code{Server/server.py} with the selected TCP congestion-control algorithm and the instrumentation flags;
  \item wait for one client connection, send the configured amount of data, and record the transfer summary;
  \item move the temporary artifacts into a permanent per-run directory under \code{DB/};
  \item for \code{my\_cca} runs, filter the kernel logs for the specific client IP and ephemeral port, then generate the analysis CSV, JSON summary, and \code{cwnd} plot.
\end{enumerate}

The Python server is responsible for the live transfer and for starting the instrumentation subprocesses. The 
log extractor repeatedly reads \code{dmesg}, appends matching kernel messages to \code{context.txt}, and clears the 
kernel ring buffer. The arrival-rate extractor uses a \code{bpftrace} probe on \code{tbf\_enqueue} to sample bytes 
entering the TBF enqueue path and writes \code{r\_arrival.txt}. The server itself accepts one client, sets the socket's 
congestion-control algorithm, sets \code{SO\_MAX\_PACING\_RATE} to 1 Gbit/s by default, sends generated data, sends 
\code{STOP}, and records transfer metadata.

The output of one run is therefore both raw and processed. The raw files, including \code{server.log}, 
\code{transfer\_summary.json}, \code{context.txt}, and \code{r\_arrival.txt}, preserve what happened during the transfer. 
The processed files, including \code{filtered\_context.csv}, \code{ip\_info.json}, and the generated \code{cwnd} plot, 
are the analysis artifacts used in the figures and tables. The sweep wrapper adds another layer above this: for each queue, burst, and token-generation rate, 
it runs the uncapped baseline, searches for an empirical \code{cwnd}, evaluates the fixed BDP-based formulas, and 
writes aggregate results under \code{sweep\_results/}.

Unless otherwise stated, the experiments use 1 GiB transfers, a base RTT around 0.4 ms, and MSS 1460 B. The physical 
topology is an isolated local network with the server and client in the same subnet. The intended bottleneck is therefore 
the server egress TBF, not the router or the wider Internet.

\subsection{Receiver-Side Window Clamp}

The sender-side cap is useful for experimentation, but a realistic client cannot normally install a custom congestion-control 
module on a remote server. Therefore the project also tested whether the same behavior can be induced from 
the client by limiting \code{rwnd}. The Python client uses:

\[
\code{SO\_RCVBUF} = \code{TCP\_WINDOW\_CLAMP} = W_{\mathrm{target}}.
\]

Since the sender transmits according to \(\min(\code{cwnd}, \code{rwnd})\), advertising a smaller receive window should 
constrain the sender even when the server-side \code{cwnd} cap is disabled.

\section{Experiment 1: Sender-Side CWND Capping}

\subsection{Parameter Sweep}

The main sweep varied the TBF queue size, burst size, and token generation rate:

\begin{itemize}
  \item \(Q_{\mathrm{config}}\) was tested as small packet-sized queues, approximately \(4p, 8p, 16p, 32p, 64p\), where \(1p = 1460\) bytes;
  \item \(B \in \{5840, 12500, 25000, 50000, 100000\}\) bytes;
  \item \(R_{\mathrm{tbf}} \in \{500, 750, 1000\}\) Mbit/s.
\end{itemize}

For each configuration, four strategies were compared:

\begin{itemize}
  \item uncapped Reno-like behavior using \code{my\_cca} with \code{cwnd\_limit = 0};
  \item an empirical cap found from physical measurements;
  \item Friedli's \(\bdp + Q_{\mathrm{config}} - \mss\) cap, referred to here as the queue-aware BDP formula;
  \item Friedli's simpler \(\bdp + \mss\) cap, referred to here as the BDP-plus-one-MSS formula.
\end{itemize}

The empirical loss threshold was 0.20 for the two smallest queue sizes and 0.05 for larger queues. This change 
should be kept in mind when comparing empirical choices across queue-size groups.

\subsection{Empirical Cap Selection}

The empirical cap was not another closed-form formula. It was a measured reference point used to understand what 
window the physical setup could actually sustain for each TBF configuration. The first step was to run the same 
configuration with normal Reno-like behavior, using \code{my\_cca} with \code{cwnd\_limit = 0}. From this uncapped run, 
the analysis extracted the post-slow-start \code{cwnd} samples before the connection entered a loss state. The useful 
samples are the top points of the Reno sawtooth: they indicate how far Reno can grow before the TBF and TCP recovery 
mechanisms push it down again. Averaging these top \code{cwnd} values gives an initial estimate of the largest safe 
window for that configuration.

The second step was to rerun the transfer with explicit server-side caps. The search started near the uncapped 
Reno top-\code{cwnd} estimate and then gradually decreased the configured \code{cwnd\_limit}. For each capped run, the 
pipeline recorded throughput and a loss rate computed from the kernel phase labels:

\[
\mathrm{loss\ rate} =
\frac{\#\{\code{loss\_recovery}\ \mathrm{rows}\}}{\#\{\mathrm{logged\ phase\ rows}\}}.
\]

The ideal target is zero loss-recovery rows. When several candidates were effectively loss-free, the higher-throughput 
candidate was preferred; when none was completely loss-free, the candidate with the smallest loss rate was used. A stricter 
diagnostic also considered \code{fast\_retransmit}. The empirical cap is therefore the cap found by physical measurement: 
it is the value that removes most of the loss-recovery behavior while keeping the transfer close to the best observed 
throughput. This empirical value is not meant to be deployable by itself; it is the ground truth used to judge whether the 
formulas from the simulation papers remain accurate on the Linux testbed.

\subsection{Early Sanity Check: Large Queue}


The first stable setup used \(R_{\mathrm{tbf}} = 1\) Gbit/s, burst size 1 MB, and \(Q_{\mathrm{config}} = 50000\) B. With 
RTT around 0.4 ms, the BDP is about 50000 B, so the original formula predicts a cap close to 66--67 MSS-sized segments. 
This experiment is documented in the project notes in \code{client\_server/README} and summarized again in 
\code{client\_server/report1/optimalCWND.md}. The measured result matched the prediction: \code{cwnd\_limit} around 
66--67 produced a flat and stable trace.

However, the throughput improvement over Reno was small: roughly 9.20 s for the capped runs versus about 9.51 s on 
average for Reno-like runs when sending 1 GiB. This is not a contradiction of the ns-3 work. Friedli's results 
already showed that once the TBF queue reaches approximately the BDP, Reno can often keep the outgoing link 
busy despite its sawtooth. The physical setup first validated this large-queue regime before moving to smaller queues.

\subsection{Why the Original Formula Overestimated}

The original algorithm assumes that the configured TBF queue can be used as extra in-flight capacity:

\[
W = \bdp + Q_{\mathrm{config}} - \mss .
\]

This is accurate when the packet arrival rate into the TBF is close to the token generation rate. In the physical setup, 
however, the server application sends in bulk and the TCP stack can enqueue into the TBF faster than the qdisc 
drains. Let \(R_{\mathrm{arrival}}\) be the short-window rate at which bytes arrive at the TBF enqueue path. 
When \(R_{\mathrm{arrival}} > R_{\mathrm{tbf}}\), the queue grows during one RTT by approximately:

\[
Q_{\mathrm{tbf}} =
\max(0, (R_{\mathrm{arrival}} - R_{\mathrm{tbf}}) RTT_{\mathrm{base}}).
\]

This queue growth is not free buffer space. It is a burst penalty that must be subtracted from the configured queue:

\[
Q_{\mathrm{effective}} = \max(0, Q_{\mathrm{config}} - Q_{\mathrm{tbf}}).
\]

The revised estimate is therefore:

\[
W =
\left\lfloor
\frac{\bdp + Q_{\mathrm{effective}} - \mss}{\mss}
\right\rfloor .
\]

When \(Q_{\mathrm{tbf}} > Q_{\mathrm{config}}\), even one RTT of enqueue/drain mismatch does not fit into the 
queue. The project used a conservative reduced-BDP branch:

\[
\bdp_{\mathrm{usable}} =
\bdp \cdot \min\left(1, \frac{Q_{\mathrm{config}}}{Q_{\mathrm{tbf}}}\right),
\qquad
W =
\left\lfloor
\frac{\bdp_{\mathrm{usable}} - \mss}{\mss}
\right\rfloor .
\]

This model explains why \(\bdp + Q_{\mathrm{config}} - \mss\) was too aggressive in many small-queue physical runs. 
For example, with \(R_{\mathrm{tbf}} = 500\) Mbit/s, RTT \(=0.4\) ms, and \(Q_{\mathrm{config}} = 50000\) B, 
the BDP is 25000 B. If packets arrive at the TBF near 1 Gbit/s, then the burst penalty is also around 25000 B. 
The effective queue is therefore about 25000 B, and the expected cap becomes roughly:

\[
\left\lfloor
\frac{25000 + 25000 - 1460}{1460}
\right\rfloor
= 33,
\]

not 50. This matches the empirical region observed in the physical tests.

This is the main reason the two ns-3 window rules do not directly transfer to every physical configuration. In many 
small-queue runs, both the empirical \code{cwnd} and the Reno top-\code{cwnd} are smaller than the values predicted by 
\(\bdp + Q_{\mathrm{config}} - \mss\), and sometimes also smaller than the simpler BDP-plus-one-MSS rule. The missing 
variable is not the token generation rate; it is the short-term enqueue rate into the TBF. When the empirical \code{cwnd} 
is used in reverse to infer what \(R_{\mathrm{arrival}}\) must have been, the resulting arrival-aware estimate is much 
closer to the measured cap. This supports the interpretation that the formulas need an arrival-pressure term in the 
physical setup.

\subsection{Remaining Model Mismatch}

The arrival-aware correction is an improvement, but not a complete model. In the very small queue cases, 
especially \(Q_{\mathrm{config}} = 6250\) B, about \(4.3p\), the reduced-BDP branch can underpredict the best empirical \code{cwnd}. 
For example, some 500 Mbit/s runs were best around \code{cwnd} 7 while the conservative formula predicted smaller values. 
The reason is that \(R_{\mathrm{arrival}}\) is 
not a stable whole-transfer constant. The relevant value is a short burst into the TBF over approximately 
one base RTT, and this value depends on offloads, pacing, qdisc behavior, and the current TCP phase.


It is important to separate two different problems that looked similar in the early notes. The full kernel ring buffer 
was a measurement problem: it made the beginning of the \code{cwnd} trace disappear, so the plots could look as if TCP 
started from an impossible state. After the background \code{dmesg} extractor was added, this artifact was greatly 
reduced. It was not the network mechanism that caused the throughput plateau.

The plateau and collapse in the small-queue experiments came from the data path itself. A bulk-sending server can 
deliver packets to the TBF enqueue path faster than the TBF token rate. During these short bursts, the configured 
qdisc queue is partly consumed before it can act as useful BDP-plus-queue headroom. If the cap is too large, this 
pressure pushes the flow into loss recovery; if the cap is small enough, the sender stays near the TBF rate without 
repeated recovery. This is why \(R_{\mathrm{arrival}}\) matters, and why the same \(R_{\mathrm{tbf}}\) and BDP can lead 
to different practical caps when the sender pacing and qdisc behavior change.

One possible follow-up would be to modify the server so that \(R_{\mathrm{arrival}}\) is intentionally controlled. 
For example, the server could expose \code{SO\_MAX\_PACING\_RATE} as an experiment parameter, add application-level 
pacing between send calls, or use \code{TCP\_NOTSENT\_LOWAT} to limit how much unsent data accumulates in the TCP stack. 
This would make it possible to run a cleaner experiment with \(R_{\mathrm{arrival}} \approx R_{\mathrm{tbf}}\), and then 
with known ratios such as \(1.25R_{\mathrm{tbf}}\) or \(2R_{\mathrm{tbf}}\). The reason this was not the main experiment 
is that the target deployment should work with an ordinary bulk sender, not only with a cooperative sender that has 
already been paced to the bottleneck rate. Pacing the server would be useful for isolating the model, but it would 
also hide exactly the burst pressure that made the physical setup differ from ns-3.

\section{Experiment 2: Receiver-Side RWND Control}

\subsection{Motivation}

Directly capping server-side \code{cwnd} is useful for controlled experiments, but it is not the final deployment model. 
For a downstream user, the limiter is usually on the path toward the receiver, and the receiver cannot assume that the 
remote server will install a custom congestion-control module. The natural receiver-side control knob is therefore 
\code{rwnd}. Since TCP sends according to \(\min(\code{cwnd}, \code{rwnd})\), the client can attempt to impose the same 
effective cap by advertising a smaller receive window.

\subsection{Method}

For each selected configuration, the server was run with \code{my\_cca} but with \code{cwnd\_limit = 0}, so the 
server-side cap was disabled. The client then ran:

\[
\code{python3 Client/client.py --rwnd-segments <empirical-cwnd>}.
\]

The client script converts the segment count to bytes using MSS 1460 B, sets \code{SO\_RCVBUF}, and sets 
\code{TCP\_WINDOW\_CLAMP}. This forces the sender's effective window to be limited by the advertised receive window.

\subsection{Results}

The receiver-side cap reproduced the sender-side empirical behavior in most cases. Table~\ref{tab:rwnd_examples} 
shows representative examples from \code{report3/RWND.md}.

\section{Experiment 3: Estimating the Token Generation Rate}

\subsection{Relation to Policing-Rate Inference}

The window-comparison experiments above assume that the TBF parameters are known. That is useful for validation: it 
lets us ask whether a good window exists when \(R_{\mathrm{tbf}}\), queue size, and burst size are controlled. A real 
receiver-side system, however, should not rely on being given those parameters. The receiver must estimate the limiter 
rate from the traffic it observes, and then advertise an \code{rwnd} cap derived from that estimate.

The natural final system would combine the two previous papers as follows:

\begin{enumerate}
  \item the receiver infers \(R_{\mathrm{tbf}}\) from arrivals, using a method such as cumulative-byte differentiation;
  \item the receiver estimates RTT;
  \item the receiver computes a target window;
  \item the receiver advertises that target through \code{rwnd}.
\end{enumerate}

The physical experiments support steps 3 and 4: once a reasonable target window is known, the receiver can enforce it 
with \code{rwnd}. The remaining challenge is step 1. Inferring the output policing rate tells us the long-term bottleneck 
rate. It does not tell us how quickly the sender is enqueueing into the TBF, nor how much of the configured qdisc queue 
is already consumed by burst pressure.

\subsection{Cumulative Arrival at the Receiver}

The cumulative-arrival method from Rimkevicius's work is still useful for estimating the bottleneck rate under 
balanced conditions. In the physical setup, the receiver records cumulative received bytes over time and estimates the 
slope after the initial transient. When the burst size is not too large and the flow is already constrained near the 
token generation rate, this slope approximates \(R_{\mathrm{tbf}}\) well enough to recover the server-side BDP used in 
the window formulas.

However, the empirical \code{rwnd} needed in the physical setup also depends on \(R_{\mathrm{arrival}}\). The receiver 
only observes delivered bytes after the TBF; it does not directly observe how fast the sender tried to enqueue packets 
before the TBF.

This explains why a receiver can estimate the BDP but still fail to choose the empirical receive window in 
aggressive bulk-send cases. The hidden variable is not the delivered rate, but the enqueue pressure at the qdisc.

\section{Limitations}

The project validates the core idea in a real Linux setup, but several limitations remain.

First, the bottleneck was implemented as a Linux server-egress qdisc. Real ISP policing is usually downstream 
of the sender and may be ingress from the user's perspective. Linux can emulate ingress shaping through \code{ifb}, 
but early tests with \code{ifb0} did not expose a clean backlog signal, so the stable experiments used server egress.

Second, RTT was very small and difficult to control precisely in the physical LAN. Some experiments attempted to 
add \code{netem} delay, but queue placement and interaction between \code{netem} and TBF changed the results. 
More complete validation should repeat the sweep across controlled RTTs.

Third, the experiments focus on Reno-like behavior through \code{my\_cca}. Cubic and BBR were studied in ns-3 
but not fully reproduced in the physical setup.

Fourth, the empirical cap search used loss thresholds that differed by queue range. This was practical 
during experimentation, but a final system should define a single objective function balancing throughput, latency, and loss.

Finally, the TBF queue, NIC driver, offload settings, and Linux pacing interact in ways that are hard 
to reduce to one closed-form formula. Disabling TSO and GSO improved interpretability, but it also means 
the setup is not exactly the default production Linux network path.

Future work should connect the window-control mechanism with a bottleneck-detection system. A Wehe-like detector~\cite{wehe} could 
first determine whether the endpoint ISP is the likely bottleneck; once that is known, the receiver-side method in this 
project could be used to choose an \code{rwnd} that uses the available queue space more efficiently. The harder open 
problem is \(R_{\mathrm{arrival}}\). If the enqueue rate is the reason the simulation formulas do not directly apply, 
then a practical receiver-side system needs either a way to estimate this hidden variable or a conservative control loop 
that can adapt without observing it directly. This is especially difficult in the small-queue regime, where the empirical 
window can be smaller than the BDP and the receiver sees only the already-shaped output stream.
