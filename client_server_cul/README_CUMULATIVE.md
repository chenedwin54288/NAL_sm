# Cumulative Byte Arrival Probe Notes

Date: 2026-06-05

This note summarizes the cumulative byte arrival work and the design discussion from today.

## What Was Added

Two new cumulative probe programs were completed:

- `Server/server_cumulative.py`
- `client/client_cumulative.py`

The cumulative server sends generated bytes to the cumulative client at a user-configured rate and duration. Its defaults are:

```text
rate:     1Gib/s
duration: 1.2 seconds
port:     9001
```

The cumulative client receives the probe stream, timestamps each socket `recv()` event, accumulates received bytes, writes a CSV, computes throughput from the cumulative byte slope, and reports a recommended receive window.

The CSV contains:

```text
sample
timestamp
elapsed_seconds
delta_seconds
bytes_received
cumulative_bytes
instant_throughput_mbit
average_throughput_mbit
```

The recommended receive window currently uses:

```text
measured_rate_bytes_per_second = total_received_bytes / elapsed_seconds
recommended_rwnd_bytes = measured_rate_bytes_per_second * RTT_seconds
```

## Integrated Server/Client Flow

`run.sh` was updated so that one server-side command can start both servers:

1. Reset the existing qdisc.
2. Apply TBF if `--tbf-rate`, `--tbf-burst`, and `--tbf-limit` are provided.
3. Initialize `my_cca` if requested.
4. Start the cumulative probe server in the background.
5. Start the normal `Server/server.py` in the foreground.

This means the TBF qdisc is already installed before the cumulative server accepts the cumulative client.

A small wrapper was added:

```text
run_server.sh
```

It forwards all arguments to `run.sh`, so every `run.sh` option can also be passed through `run_server.sh`.

Example server command:

```bash
./run_server.sh \
  --cca my_cca \
  --size-gib 1 \
  --rtt-ms 0.4 \
  --rate-mbit 250 \
  --tbf-rate 250Mbit \
  --tbf-burst 50000b \
  --tbf-limit 6250b \
  --cwnd 0
```

A client-side helper was added:

```text
run_client.sh
```

It performs the manual tester flow:

1. Run `client/client_cumulative.py` against the cumulative server.
2. Read `recommended_rwnd_bytes` from the cumulative client summary JSON.
3. Run the normal `client/client.py` using `--rwnd-bytes`.

Example client command:

```bash
./run_client.sh --host 192.168.88.254 --rtt-ms 0.4
```

## Important Discussion Points

### TBF bottleneck vs server pacing

If the cumulative server sends below the TBF token generation rate, then the TBF is not the bottleneck.

Example:

```text
server probe rate = 20 Mbit/s
TBF rate          = 250 Mbit/s
```

In this case, the measured cumulative arrival rate should be around `20 Mbit/s`, but that is because the server is application/pacing limited. It is not discovering the `250 Mbit/s` TBF bottleneck.

To make the TBF visible in the cumulative byte slope, the probe send rate must be higher than the TBF rate.

### Current method vs packet-level method

The paper-style cumulative byte arrival method uses packet timestamps from receiver-side pcap:

```text
for each received packet:
  cumulative_bytes += packet_payload_length
  derivative = delta(cumulative_bytes) / delta(time)
```

The current implementation uses socket `recv()` timestamps instead:

```text
for each recv() event:
  cumulative_bytes += len(received_payload)
  derivative = delta(cumulative_bytes) / delta(time)
```

This follows the same cumulative-slope idea, but it is not packet-granular. TCP is a byte stream, so one `recv()` can contain data from multiple packets. The instantaneous derivative can look bursty, especially on short probes, but the whole-probe average is useful for a practical runtime `rwnd` estimate.

We decided to keep the current `recv()`-based method for now because it is easier to run and does not require tcpdump, root permission, pcap parsing, or packet offload handling.

### Why the current estimator returned 8 when empirical best was 5

For the experiment:

```text
TBF rate  = 250 Mbit/s
RTT       = 0.4 ms
TBF limit = 6250 bytes
```

The cumulative client measured roughly the bottleneck delivery rate:

```text
250 Mbit/s = 31,250,000 bytes/s
```

Then it computed:

```text
rwnd = 31,250,000 * 0.0004
     = 12,500 bytes
     ~= 8.56 MSS
```

So the client recommended about `8` or `9` MSS.

However, the real empirical best was about `5` MSS. That is because the small TBF queue changes the best safe window:

```text
6250 bytes / 1460 MSS ~= 4.28 MSS
ceil(...) = 5 MSS
```

The key point is that the current one-shot cumulative byte method estimates the BDP-like window:

```text
rwnd ~= measured_delivery_rate * RTT
```

It does not directly reveal the hidden server-side TBF queue size.

### Why cumulative bytes alone cannot always give the empirical optimum in one probe

A single cumulative-byte curve tells the receiver how fast data arrived. It does not uniquely identify the queue size or whether a larger window caused extra queue pressure or loss inside the path.

Several windows may produce nearly the same receiver-side arrival slope once the bottleneck is saturated:

```text
rwnd = 5 MSS  -> near 250 Mbit/s
rwnd = 8 MSS  -> near 250 Mbit/s
rwnd = 12 MSS -> near 250 Mbit/s
```

The delivery rate can look the same, while queueing/loss behavior differs. Therefore, one cumulative probe can estimate the delivery capacity, but it cannot always estimate the smallest empirical safe window.

To estimate the empirical optimum using only cumulative received bytes, the client would need to run a sweep:

```text
probe rwnd = 1 MSS
probe rwnd = 2 MSS
probe rwnd = 3 MSS
...
choose the smallest rwnd whose cumulative-byte slope reaches the throughput plateau
```

This would still use only receiver-side cumulative bytes, but it would require multiple probes instead of one.

## Current Recommendation

For now, use the implemented cumulative probe as a practical BDP-style receive-window estimator:

```text
rwnd = measured_rate * RTT
```

For experiments where the empirical optimum is lower because of a small hidden TBF queue, remember that a one-shot cumulative receive curve may overestimate the best safe `rwnd`.

Future improvement:

```text
Add a multi-probe client-side rwnd sweep that uses cumulative-byte slopes only.
```
